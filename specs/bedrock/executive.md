# Bedrock - Executive Summary

## Requirements Summary

Bedrock provides the core conversation state machine for PhoenixIDE. Users interact with an LLM agent through a reliable, predictable execution model: messages move through explicit idle, LLM, tool, cancellation, error, continuation, and approval states; tools execute serially; cancellation synthesizes tool results when needed to preserve transcript/API integrity; retryable versus non-retryable failures stay distinct; and committed transcript history survives restarts.

Current normative authority is `requirements.md` for timeless rules and `bedrock.allium` for precise lifecycle/state-machine behavior. Persisted provider prompts use one strict, generation-fenced database projection per current transcript member; continuation freezes that same authority before provider work. ADR-026 records lifecycle-versus-WorkScope ownership; ADR-031 records first-class ProductConversation persistence and its staged single-authority cutover; ADR-032 retires Project authority and leaves repository context derived through the attached WorkScope; ADR-036 records process fail-stop when local SQLite authority cannot be established.

## Current Reality

The implementation still retains legacy Project/mode and terminal compatibility surfaces. The durable conversation row carries `ConvMode` (`Direct`, `Explore`, `Work`, `Branch`), task approval parks in `AwaitingTaskApproval`, and `/abandon-task` and `/mark-merged` remain live compatibility endpoints. ProductConversation routes own the canonical blocking task-approval overlay and action copy for healthy aggregate views, while degraded standalone/fallback transcript routes retain their own approval surface so AwaitingTaskApproval never loses approve/reject/feedback controls. ProductConversation is now the stable aggregate identity and ordinary Open/History lifecycle authority for list, snapshot, and detail reads; transcript members retain message persistence, SSE, runtime/provider sessions, and generation-fenced prompt projection. Successful durable Close retirement retires the attached WorkScope, records one outcome message, transitions the aggregate to History in the completion transaction, and publishes compatibility updates only after commit. Dedicated Close-start replacement and removal of legacy endpoint and continuation edges remain incomplete. Phoenix continues using the current Project-backed repository model; replacement is deferred until a named feature requires it. The local SQLite fail-stop doctrine is adopted. Runtime admission fencing covers unclassified local authority loss, including continuation provenance reads; broader SQLite-boundary coverage remains incomplete.

## Technical Summary

Implements Elm Architecture with a typed-effect executor boundary. The SM has two pure entry points: `handle_user_event()` for API-initiated events and `handle_outcome()` for executor results. Effects carry oneshot channels typed to their expected outcome (`LlmOutcome`, `ToolOutcome`, `SubAgentOutcome`, `PersistOutcome`) — the compiler prevents invalid event/state combinations. Persistence uses `CheckpointData::ToolRound` which structurally requires matched `tool_use`/`tool_result` pairs. Error classification is exhaustive with no `Unknown` variant. Executor loop uses `StepResult::Terminal` to force explicit exit on terminal states. Token streaming uses fire-and-forget `StreamToken` effects routed to SSE without SM state transitions. Sub-agents have mandatory timeouts. The normative fan-in target removes each exact accepted child from pending, makes duplicate terminal acceptance idempotent, and prevents ordinary parent settlement while admitted children remain pending. On server restart, ordinary interrupted conversations resume from idle with full message history preserved. Interrupted `present_svg` invocations recover an already committed compact artifact reference by exact assistant/tool identity; invocations without a committed snapshot retain the interrupted error. A committed steering turn whose accepted user or skill message is still awaiting its first response preserves `LlmRequesting` from immutable receipt/transcript evidence; a synchronous recovery dispatch failure settles as a persisted typed error, and a failed error write retires the runtime for reconstruction. Durable continuation operations retain their operation identity and recovery state.

### Terminal startup acknowledgement

`ConversationRuntime::run_inner` explicitly acknowledges successful startup settlement before its terminal return. Startup discovery can select `ContextExhausted` through retained steering rows; that path preserves the persisted state and queue, starts no provider request, and must not abort recovery of later conversations. Interrupted and fatal startup exits retain their failure semantics. Executor coverage for the retained-queue case, an acknowledgement assertion for expired sub-agent overload, and a canonical database-backed `RuntimeManager` recovery-pass regression are authored; hosted Rust execution remains pending. Local formatting/task checks do not qualify runtime behavior.

## Opening settlement repair

REQ-BED-021's atomic pending-intent consumption is enforced for live opening inserts and for already-persisted manual openings during forward upgrade. Migration 113 reconstructs a completed handoff only from an unambiguous raw or canonical opening identity, exact typed user handoff content, manual opening authority, valid same-aggregate predecessor/successor topology, and one decodable predecessor continuation message. It records the receipt and consumes the intent in the migration-ledger transaction without replaying an opening or changing transcript bytes. Missing, mismatched, conflicting, ambiguous, and generated-context evidence is preserved rather than inferred accepted. The normal send-chat and authority gates are unchanged.

`forward_upgrade_settles_already_persisted_canonical_continuation_opening` reproduces the historical raw-key trigger miss through migrations 045, 074, and 100. `historical_continuation_*` tests verify byte preservation, raw/canonical identity, idempotence, conflict preservation, negative fences, and full transaction rollback/retry. `historical_manual_opening_repair_unfences_service_chat_only_with_matching_evidence` exercises real send-chat rejection before migration and ordinary-chat admission afterward while unresolved openings remain fenced. This is a correction of existing opening acceptance/settlement behavior, not a general database recovery or opening replay guarantee. Production application and post-upgrade owner execution remain separate deployment acceptance evidence.
