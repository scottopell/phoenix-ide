# Phoenix Compatibility Guarantees — Executive Status

## Protected exact launchd schema-129-to-129 private refresh

REQ-COMP-018 defines one private native macOS launchd refresh whose complete source and target ledgers are the exact migration-129 registry. Each transaction dynamically authenticates and binds its full candidate SHA and preparation-receipt digest, complete registry/ledger proofs, separate clean controller/helper identities, and canonical database path. Native SQLite backup-API evidence and one sequential isolated rehearsal are mandatory; no live migration or live reconciliation is permitted. A durable phase/`migration_started` marker precedes candidate startup: before it only a proven unchanged predecessor may restart, while after it the transaction is fail-stopped and candidate-only with `finalize-current` as the sole continuation. Same-ledger equality does not override phase or proof authority. Successful backup and unresolved evidence remain retained and claim-bound; all other routes and bypasses are rejected.

This documentation records the normative boundary only. Implementation, hosted qualification, runtime acceptance, and production activation are not claimed; no test was run.

## Current reality

Phoenix supports forward SQLite migrations, but compatibility guarantees have not previously had one project-wide authority. Some feature tests and implementations therefore provide stronger cross-version behavior than a named product requirement demands.

Unprotected ordinary production deployment has runtime-artifact recovery that restores the previous binary, configuration, environment, and service state after failed activation, subject to its qualified compatibility boundary. It does not restore a matching database, so its existing outcome is runtime-artifact rollback. The release-update UI still describes that outcome as the previous release being “restored and verified,” which overstates the database guarantee. Phoenix also still accepts an older release candidate without proving that its paired database backup was restored. Phoenix does not provide a general automatic database rollback subsystem. Manual version rollback is offline: stop Phoenix, restore the database backup paired with the target binary, then start that binary. Task 44016 owns the deployment rejection boundary and truthful rollback messaging.

Database restore or replacement is an offline operator procedure. Phoenix does not provide live replacement fencing for an SQLite file already opened by a running process.

The narrow prepared-artifact launchd exception admits either the exact migration-123 baseline or a source ledger exactly equal to the migration-128 candidate registry under ADR-105 and ADR-114, including named migrations 126/127/128 and immutable registry/digest checks. The 128-to-128 controller and regression changes are authored; hosted CI qualification is pending. Both sources require an offline snapshot and mandatory candidate `--migrate-only` invocation, permit automatic predecessor rollback only before invocation with unchanged transaction-bound source contents, and forbid snapshot replay or predecessor startup afterward. This is one bounded prepared replacement, not a general same-version, cross-binary, downgrade, or runtime compatibility guarantee.

[ADR-115](../adrs/115_protect-exact-114-to-128-published-release-activation.md) adds one commissioned protected published-release admission: the exact complete candidate-registry prefix through 114 to the exact target 128. The release supplies the candidate binary and registry; a separately explicit controller commit, not the release commit, supplies the retained hash-bound helper. It reuses the full protected snapshot/capacity/exclusivity and durable `migration_started` lifecycle, including candidate-only recovery after invocation. Prepared exact-123/exact-target and ordinary exact-123-to-128 admission remain unchanged. Documentation is authored; controller/regression qualification, runtime and deployment acceptance are not established by this documentation change. Ordinary unqualified pending migration intervals must reject before disruption, not silently fall back to artifact rollback.

The ordinary launchd in-place route does not gain a backup requirement. For the same exact 123-to-128 interval, the authored policy retains immutable registry/digest evidence and treats the first candidate startup attempt as a conservative downgrade boundary: later failure retains the candidate and stops forward-only because migration or initialization writes may already have committed. Hosted CI qualification remains pending.

The protected systemd published-release contract is separately bounded by REQ-COMP-014 / REQ-PD-023–027 and [ADR-116](../adrs/116_protect-exact-65-to-128-systemd-published-release-activation.md): exact prefix65 to fixed RC4 target128, independently pinned controller/helper, preserved configuration, pristine offline backup and isolated exact-candidate rehearsal before the durable live marker. Persistent verified service/socket inhibits survive disruption/reboot; removal requires authorized predecessor artifact restoration or exclusively verified exact-target candidate startup. This does not extend launchd or qualify any other source/target.

Its expanded regressions require successor hosted execution; local validation is limited to Python compilation and diff whitespace checks.
