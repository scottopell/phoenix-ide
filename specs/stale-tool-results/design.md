# Stale Tool Result Clearing — Design

## Where this lives (REQ-STR-009)

Tool-result clearing is a transform applied while the conversation history is
assembled into the provider-agnostic message list, in
`Executor::build_llm_messages_static`. That function reads the persisted
messages for a conversation and folds them into `Vec<LlmMessage>`; clearing is a
retention pass over that fold, before any provider translation
(`anthropic.rs::translate_request`, the OpenAI Responses translation) runs. A
single pass therefore governs every provider identically, and the persisted
`db::ToolContent` it reads from is never mutated.

This generalizes an existing narrower transform in the same function: aged
screenshots are already dropped from replayed history by
`tool_msg_indices_keeping_images`, which keeps image blocks only for tool-result
messages within the most recent rounds and replaces older ones with a text
placeholder. Stale tool-result clearing extends that same round-anchored,
non-destructive, placeholder-leaving shape from images-only to the full textual
body of a tool result.

## The retention model (REQ-STR-001, REQ-STR-003, REQ-STR-007)

Retention is anchored to **tool rounds counted from the end of the
conversation**, not to message age in wall-clock time or to a recomputed token
budget. A tool round is one assistant turn's batch of tool calls plus their
results. The most recent `keep_recent_rounds` rounds are the *retained window*;
their tool results are sent in full. Rounds older than the retained window are
the *clearable region*.

Round-from-end anchoring is what makes removal stable across turns
(REQ-STR-007). As the session grows, a round only ever moves *further* from the
end — never closer. So a result that is outside the retained window on one turn
is still outside it on every later turn: once cleared, it stays cleared, with no
per-turn recomputation that could resurrect it and shift the first changed token.

A result in the clearable region is cleared only when **all** of these hold:

1. **Activation (REQ-STR-001).** The estimated input tokens for the assembled
   request exceed `clear_trigger`, a fraction of the model's `context_window`.
   Below that high-water mark the conversation is short enough that the whole
   transcript fits comfortably, and nothing is cleared — the retained window is
   effectively the entire history. Within a single conversation, input-token
   usage only grows, so activation is itself a one-way transition: the trigger is
   crossed at most once and never un-crossed, which keeps activation from
   flapping the cleared set.

2. **Recoverability (REQ-STR-002).** The tool that produced the result is
   *clearable* — its output can be regenerated by re-invoking it. Clearability is
   a property of the tool, declared on the `Tool` trait (see below), not a
   property inferred from the result's content.

3. **Worthwhile gain (REQ-STR-006).** The total tokens freed by clearing the
   eligible results on this turn is at least `clear_at_least`. If the eligible
   set would free less than that, the pass clears nothing this turn and waits for
   more clearable output to accumulate. This bounds how often a removal disturbs
   the cached prefix.

## Recoverability is a tool capability (REQ-STR-002)

The `Tool` trait gains a clearability capability:

```rust
trait Tool {
    // ...
    /// Whether a stale result from this tool may be cleared from the model's
    /// view. True only when re-invoking the tool reproduces the information —
    /// the result carries no state that cannot be recovered.
    fn clearable(&self) -> bool { false }
}
```

The default is `false`: a newly added tool is never silently cleared. A tool
opts in only when its output is reconstructable by re-invocation. The read-heavy
tools whose output dominates a long session opt in — `read_file`, `bash`,
`search`, `keyword_search`, `read_image`, the browser read tools, the tmux and
terminal history tools, `process_inspection`. Tools whose result is
unreproducible or consequential do not: `ask_user_question` (the human's typed
answer cannot be regenerated), `think`, `propose_task`, the subagent
`submit_result` / `submit_error` handoffs, and `patch` (its result records a
mutation that re-invocation would not reproduce).

A `false` default plus an explicit per-tool opt-in makes "this tool was never
considered for clearing" structurally distinct from "this tool's output is safe
to clear" — the recoverability decision is in the type, not in a comment or an
allowlist that drifts from the tool set.

The clearing pass needs the tool name for each tool result to look up
clearability. The tool name is carried on the assistant `ToolUse` block paired
with each `ToolResult` by `tool_use_id`; the pass joins results to their calls on
that id to resolve the producing tool.

## What clearing produces (REQ-STR-004, REQ-STR-005)

Clearing a tool result replaces the textual body sent to the model with a fixed
placeholder — `[tool result cleared to save context]` — and sends no image
blocks for it. The paired assistant `ToolUse` block is left untouched, so the
model still sees that the call was made and with what arguments; only the result
body is elided. This mirrors the existing screenshot placeholder and the
provider-level guarantee that a tool result always has its tool call present.

The clearing decision is represented as a typed verdict per tool-result message,
not as an in-place string mutation threaded through the fold:

```rust
enum ToolResultRetention {
    /// Send the result body and images verbatim.
    Kept,
    /// Replace the body with the placeholder and drop images.
    Cleared,
}
```

The retained `db::ToolContent` in storage is the single source of truth and is
read-only here; the cleared form exists only in the `Vec<LlmMessage>` handed to
the provider for one request. Because the cleared form is computed on every
assembly and never persisted, there is no serialized "cleared" state that could
be lost on a write or need a migration — REQ-STR-005 holds by construction, and
a reconnecting UI that rebuilds from storage shows the full result.

## Interaction with prompt caching (REQ-STR-006, REQ-STR-007)

Prompt caching reuses the longest request prefix that is byte-identical to a
prior request. Tool results are carried in user-role messages, so clearing a
result in the clearable region changes a user message and moves the first
differing token earlier — invalidating the cached prefix from the earliest
cleared message forward. This cost is unavoidable for any in-place context
reduction; the design bounds it rather than pretending to avoid it:

- **One-time, then re-warmed.** The turn on which a result first becomes cleared
  pays a cache write for the new, shorter prefix. Because clearing is stable
  (REQ-STR-007), every subsequent turn sends the *same* cleared prefix and reads
  it from cache. The invalidation is paid once per batch of removals, not per
  turn.

- **Batched to be worth it (REQ-STR-006).** `clear_at_least` ensures each
  invalidation frees enough tokens that the one-time cache-write cost is
  recovered by the ongoing savings. A removal that would free a trivial amount is
  deferred until enough clearable output accumulates.

- **The cached tail is never disturbed.** The Anthropic translation places three
  deterministic cache breakpoints (`AnthropicCacheBreakpointsPlaced` in
  `specs/llm/anthropic.allium`): the last system block, the last tool entry, and
  the last cache-bearing block of the last user message — which, during a tool
  loop, is the trailing tool result. The retained window (REQ-STR-003) always
  contains that trailing result, so breakpoint (3) lands on an uncleared block.
  Clearing only ever touches the prefix *before* the retained window; the
  current turn's reusable anchor is intact.

- **Cache key is unchanged.** Requests continue to use
  `PromptCacheKey::stable(conv_id)`. The cleared prefix is a property of the
  message content, not the cache cohort; keeping the key stable lets the
  re-warmed shorter prefix be reused by the same conversation's later turns.

## Token estimation (REQ-STR-001, REQ-STR-006)

Activation and the `clear_at_least` gain calculation both need token counts.
They reuse `estimate_text_tokens`, the same estimator that `cap_messages_to_-`
`token_budget` and the continuation overflow guard use, so the high-water-mark
decision is consistent with the other token-budget logic in the executor.
Estimation is approximate by design — the trigger is a safety margin below the
true window, and the consequence of a slightly-off estimate is clearing one
round early or late, never a dropped result or a 400.

## Relationship to compaction and screenshot pruning

Three retention mechanisms coexist in history assembly, in increasing order of
loss:

- **Screenshot pruning** drops only images from aged tool rounds, keeping their
  text. It is the narrowest and runs always.
- **Stale tool-result clearing** (this spec) drops the full body of aged,
  clearable, recoverable results once the high-water mark is crossed. Mid-weight:
  the information is recoverable by re-invocation.
- **Continuation / summarization** (`request_continuation`, `flatten_tool_blocks`,
  `cap_messages_to_token_budget`) is the heaviest and last resort: it collapses
  the whole transcript into a summary when the window is nearly full. It is lossy
  in a way clearing is not, because a summary cannot be re-expanded.

Clearing reduces how often the heaviest mechanism is reached: by holding the
input-token curve down across a long session, it pushes the point at which
summarization becomes necessary much later, or out of reach entirely for most
sessions.

## Configuration (REQ-STR-010)

Three parameters govern retention, resolved per conversation from the model's
context window and deployment configuration:

| Parameter | Meaning | Default basis |
|---|---|---|
| `clear_trigger` | Input-token high-water mark that activates clearing | A fraction of `context_window`, leaving headroom for the model's reply |
| `keep_recent_rounds` | Tool rounds whose results are always retained in full | Enough rounds to cover the agent's active working set |
| `clear_at_least` | Minimum tokens a removal must free, or it is deferred | Large enough that a cache write is recovered by the savings |

The defaults are chosen so a short session clears nothing and a long session on a
large-window model clears steadily; a smaller-window model crosses `clear_trigger`
sooner and clears earlier. Concrete default values are tracked in `executive.md`.
