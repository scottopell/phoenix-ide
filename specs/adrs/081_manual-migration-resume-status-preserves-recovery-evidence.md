# ADR-081: Manual migration resume status preserves recovery evidence

- **Status:** Accepted
- **Date:** 2026-10-05
- **Affects:** launchd deployment, release updates, compatibility

## Context

The explicit ordinary migration policy in ADR-080 resumes a captured predecessor only after manual offline matched database restoration. Its terminal status must remain readable by that predecessor. The established `activation_failed_rolled_back` terminal state is understood, but its old embedded update UI labels database restoration as absent and its API omits recovery mode. A source change cannot replace that already captured binary's UI. Claim removal also needs directory durability, and completed last-transaction evidence must not be mistaken for active deployment ownership.

## Options considered

1. Add a new terminal state or force a recovery-aware predecessor upgrade: rejected; the captured predecessor would not understand the state, and replacing its bytes breaks matched recovery.
2. Treat generic rollback wording as sufficient: rejected; manual matched restoration would be reported as no restoration.
3. Preserve the existing terminal state, thread optional recovery mode in the current API/UI, and retain an explicit explanation in the existing failure diagnostic: selected. The captured predecessor can display the explanation without assuming it gains new UI behavior.

## Decision

Successful manual resume records `activation_failed_rolled_back` with `recovery_mode = migration_resumed` and an explicit failure diagnostic stating that manual matched restoration was verified, the captured predecessor resumed, and no automatic database restore occurred. The current API projects recovery mode; the current UI uses specific manual-restoration wording when present and generic runtime-verification wording when absent, displaying the diagnostic in either case. The old captured API/UI receive only their supported state/diagnostic fields. Their embedded heading is not replaced, and the explicit diagnostic is the bounded old-predecessor fallback.

The helper fsyncs the claim directory after owned unlink under the claim lock. If that fsync fails, it re-establishes matching ownership for verification-only terminal retry, without changing terminal status or replaying runtime/database work. If the removal is already absent, the same terminal evidence can be verified and the parent fsynced idempotently; a competing owner refuses finalization. CLI retained-migration instructions require actual active ownership, not the last transaction ID.

## Consequences

Recovery meaning travels through each supporting status surface without inventing an automatic database rollback guarantee or a generic status framework. The immutable predecessor's generic heading can remain imprecise, but the same visible status includes the explicit manual-restoration explanation. Optional recovery mode permits a current UI to consume the captured predecessor's narrower API. Cross-surface regressions consume statuses generated by the disposable failed-activation/manual-restore/resume lifecycle, including post-unlink fsync failure and claim-free CLI status. Full hosted Rust qualification remains necessary for the production API integration.
