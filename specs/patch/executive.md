# Patch Tool - Executive Summary

## Requirements Summary

The patch tool enables precise file editing through six operations: replace (substitute unique text), insert_before / insert_after (place content adjacent to a unique anchor without altering it), append_eof, prepend_bof, and overwrite (creates files). Anchor-based operations require oldText to match exactly once, preventing ambiguous edits. Missing and duplicate anchor errors identify the failing patch's 1-based array position and operation, so multi-patch calls do not leave the agent guessing which request failed. When duplicate matches remain ambiguous after safe matching strategies, the error reports the total match count plus bounded line-numbered snippets so the agent can widen oldText without an extra search cycle; missing-anchor errors direct the agent to refresh the file and retry that patch with current text. A replace may opt into replaceAll to substitute every exact occurrence, the explicit escape hatch for mechanical multi-site refactors. Multiple patches per call are applied atomically against original content, with overlapping edits rejected rather than silently merged—if any fails, the file remains unchanged. On success the applied unified diff is returned to the agent as well as the UI, so edits can be confirmed without re-reading the file. Clipboards enable cut/copy/paste workflows that persist across calls, reducing transcription errors when moving code. Reindentation adjusts whitespace when moving code between indentation levels. Fuzzy matching recovers from minor whitespace differences in LLM-generated patches. Autogenerated files trigger warnings but patches apply anyway.

## Technical Summary

Implemented as a Tool trait with schema for path and patches array. Each patch specifies operation, optional oldText/newText, optional replaceAll flag, optional clipboard names, and optional reindent config. Every operation lowers to a located Edit (offset, length, replacement); the insert operations and replaceAll add no new application machinery — insert_before/insert_after are zero-length edits at the matched anchor's start/end, and replaceAll emits one edit per exact occurrence. All edits are collected against original content and applied in descending offset order for atomicity; overlapping byte ranges are rejected. Fuzzy matching (exact, dedent, line trimming, Unicode skeleton) applies to single-anchor location only; replaceAll matches exact occurrences exclusively. The matching layer returns typed missing/non-unique outcomes; the planner adds the failing patch's 1-based request position and operation without duplicating that context inside matching. Duplicate-match failures carry bounded diagnostics with total count, 1-based start lines, and concise snippets. Clipboards stored in HashMap on PatchTool struct, persisting within conversation. Reindentation strips then adds prefixes line-by-line, failing if strip prefix not present. The applied unified diff is returned to the agent (bounded, truncation noted) and to the UI.

## Production Review Baseline

A read-only production review covering 2026-05-10 through 2026-07-10 observed 4,732 patch calls and 606 marked tool errors. Five were classified as infrastructure/session failures. Of the remaining errors, 303 were non-unique anchors, 265 were missing anchors, 21 were overlaps, and 12 were other patch errors. Missing and non-unique anchors therefore accounted for 568 of 601 non-infrastructure errors.

Turn-level model attribution matched all 4,732 calls to a `turn_usage` record within one second (maximum observed distance 0.686 seconds): 4,181 calls used `gpt-5.5`, 314 `gpt-5.6-sol`, 190 `gpt-5.4`, and 47 `gpt-5.4-mini`.

A bounded aggregate trajectory review found that 420 of 568 anchor failures occurred in calls containing multiple patches. After missing-anchor failures, 221 of 265 trajectories performed a read or search before a same-file retry; after non-unique failures, 221 of 303 retried the same file directly. These results selected request attribution—not another permissive matcher—as the intervention: the planner reports the failing patch's 1-based array position and operation while matching remains unchanged.

The post-deployment review uses the exact `Phoenix IDE starting` startup record containing this change's `git_sha` as the preferred boundary. If that marker is not retained, the first observed error beginning with `Patch N (operation) failed:` is reported explicitly as a rollout proxy. Evaluation reports patch calls and adjusted marked-error rate, missing/non-unique counts, next-patch success within ten minutes, model-attribution coverage, stable-model cohorts, absolute and relative changes with confidence intervals, and a sensitivity window excluding development dogfooding. Statistical significance is not claimed until sufficient post-deployment volume exists.
