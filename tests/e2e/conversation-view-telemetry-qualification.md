# Conversation-view telemetry: bounded candidate qualification

This is the ready execution contract for extending the existing history real-server/browser qualification, not a second framework or a recorded acceptance result. Application requirements are `specs/conversation-view-telemetry/requirements.md`. Source tests are not runtime qualification.

## Authority and trigger

Use the existing harness-only PR903 workflow, `tests/e2e/history_browser.py`, and `ui/scripts/qualify-history-realserver.mjs`. The harness owns its isolated mock-provider server, ephemeral database, loopback Vite preview, pinned Chromium, teardown and artifacts. No production endpoint, credential, external provider, public preview, local Rust build, new workflow family or persisted capture service.

Execute one final joint hosted build/run only after the project coordinator provides (1) the qualified immutable history repair, (2) the integrated telemetry application SHA with exact source CI/review, and (3) a committed harness extension SHA. Keep the two checkouts distinct. Bind application Git SHA, UI/binary hashes, frontend source/dirty stamp, backend source/instance, fixture hash, harness SHA and Chromium version in the existing build/result receipts. Build before stamping immutable artifact hashes. Harness changes and synthetic environment settings are not application-source evidence. Older-stack trials are provisional and cannot qualify the final integrated application.

The concrete present infrastructure gap is exporter isolation: `tests/e2e/run.py::_server_env` forces `PHOENIX_TRACE_EXPORTER=none` and removes every inherited `OTEL_`/`DD_` value; the history harness retains this environment. Existing history receipts therefore cannot demonstrate trace retrieval. Extend only the harness's post-scrub synthetic environment. Reserve this hunk with its owner before editing.

## Isolated retrievable export

Start an ephemeral loopback-only OTLP HTTP/protobuf receiver alongside the existing owned processes, using `view_telemetry_sink.py` and the pinned official `opentelemetry-proto` decoder (no collector daemon), not Phoenix production VictoriaTraces. Set only synthetic `PHOENIX_TRACE_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf`, a receiver-owned loopback `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, and a unique service/run identity after the environment scrub. Do not restore inherited exporter headers, credentials or destinations. Fail setup if the receiver is unavailable or an endpoint is not loopback.

Retain exported trace bytes plus a decoded, allowlisted browser-span index under the existing private candidate artifact. Bound the receiver to 8 MiB total, 256 batches, 10,000 spans and the existing browser wall deadline; overflow is explicit failure, never silent truncation claimed as complete. Stop it with the existing owned-process teardown. The limits are harness budgets, not product guarantees. Wait for a bounded exporter flush and fail retrieval if expected identified spans are absent; HTTP 204 ingestion alone proves neither export nor retrieval. The sink persists each accepted protobuf batch and atomically replaces its decoded bounded index (not a cross-file atomic transaction); after drain/teardown `final_index` must reconcile raw batch counts/bytes and late error state before acceptance; `retrieve`, `validate_view` and `validate_correlations` check uniqueness, actual parent/trace identity, expected lifecycle/source/instance/timing fields, strict browser attribute projection and exact correlation set. The caller must wait for all expected exports under an absolute flush deadline and fail if absent; no daemon memory-only acceptance receipt is sufficient. Sink tests exercise official protobuf encoding plus actual loopback HTTP semantic retrieval and rejected transport.

Identify spans first by the synthetic service/run and the captured UUID `open.id`; inspect full traces only for those identified trace IDs. Require one `browser.conversation_view` per admitted reported journey, at most sixteen `browser.view_correlation` children and exact authoritative source/instance fields. The report trace need not equal an earlier API request trace: correlation children join them through opaque request/stream IDs and optional `trace` correlation entry. Validate finite API-response trace IDs against retrieved server traces when supplied. The server trace must contain a non-browser server span in a trace distinct from the report trace; a correlation that points only to the browser report itself is not evidence of server retrieval. Global initial `coordinator.history_open` must match its actual request `open.id`; older-page fetches must not become additional initial-open spans. A missing traceparent stays null, never fabricated.

## Browser cases and sampling

Reuse the two existing synthetic ordinary/Global aggregates and real HTTP/SSE, without route/response stubs. Observe report POST metadata/body and finite response headers only; never copy conversation response bodies into telemetry receipts. Distinct private sentinel transcript, breadcrumb, tool and route text must be absent from report JSON and allowlisted browser-span attributes. Actual synthetic history screenshots may remain in the separate existing history evidence, not in telemetry payloads.

Production sampling stays 25%. Do not add a public sampling knob or globally replace `Math.random` and claim unbiased application overhead. Pure tests already control admitted/sampled/unsampled cases through injected reporter randomness and transport. For real-browser runs, use fresh contexts and classify admission from actual correlated requests/report counters; bounded reruns obtain naturally sampled and unsampled observations. Retain every raw trial, including misses, failures and dropped reports. Maximum 64 fresh contexts, at most sixteen reports per case, existing five-minute browser/outer server bounds. Failure to obtain the minimum comparison cohorts within the budget is inconclusive, not a reason for unlimited retries or a sampling change.

Cases:

1. Ordinary and Global initial opens: ready report requires current visible transcript, visible actionable breadcrumb and actual current target or tail. Report marks are monotonic-client first observations; compare breadcrumb-minus-transcript frame estimates, not pixels or wall-clock server subtraction.
2. Exact predecessor/Back/reload: fresh journey IDs and request correlation; no readiness from navigation inventory, skeleton, empty virtual slots, hidden ancestors or stale target disposition. Use the existing real history checks as presentation ground truth.
3. Foreground/background: actual page visibility via a second tab where Chromium supports it. Record the browser's observed visibility; do not label synthetic dispatched events as physical suspension. No new readiness while hidden. Return foreground and verify current content before completion.
4. Standalone/BFCache resume: the synthetic hook tests prove event-state semantics; hosted Chromium must report actual standalone/BFCache capability. If unavailable, record uncovered status rather than labeling manually dispatched events genuine PWA/BFCache. Fresh resumed journey uses retained identity but fresh owning/rendered evidence, not old settlement marks.
5. Canceled/incomplete: leave a pending real admission or hide/unmount before readiness, then observe the best-effort terminal outcome. Use explicit lifecycle/navigation signals, not arbitrary sleeps to manufacture completion. A failed/offline send must stop within its three-second transport deadline with no retry/offline queue.
6. Collector negatives on the same disposable authenticated server: unknown/private fields, invalid UUID/enum, too many correlations, unbounded/censored-duration contradictions and oversized body are rejected and produce no accepted browser-view span. Unauthenticated request is denied. These are Phoenix API negatives, not malformed OTLP posts: a rejected OTLP transport intentionally fails the whole positive capture and belongs in a separate sink unit trial. Retain status and bounded schema diagnostics, never credentials.

## Overhead and volume comparison

Use the existing Playwright Chromium CDP session on the *same final application build*. Capture raw `Performance.getMetrics` deltas (TaskDuration, ScriptDuration, LayoutDuration, RecalcStyleDuration), bounded long-task/frame samples, telemetry payload bytes and network/event counts around a readiness-bracketed identical journey. Exclude framework mount/network readiness only when the measured scenario explicitly starts after that readiness condition; retain separate end-to-end open timing. Apply one fixed documented CPU throttle and viewport, warm up once, then classify at least eight naturally sampled and eight unsampled trials across matched ordinary/Global scenario strata. Do not average away per-run data or mix application builds. Sampling assignment is observed randomness, not a forced equivalent zero-instrumentation build: unsampled reporter admission overhead is common to both arms and must be described.

Report raw cohorts, median/intervals, pairing/strata, noise floor and any effect estimate. Small/noisy cohorts are inconclusive. Structural checks remain mandatory regardless of noisy timing: one telemetry POST maximum per report, no per-frame/per-row HTTP or log spans, no retry queue, eight-KiB report body, sixteen correlations, bounded observer candidates/counters, no additional transcript reads/positioning commands caused by telemetry, no capture/receiver overflow. Record CPU/heap/frame observations as estimates, not compositor proof. Relative overhead clearance requires independent review of raw observations and the agreed noise/budget criterion; do not invent a pass threshold after seeing results.

## Receipts and honest exit

Extend existing assertion/result JSON with app/harness/fixture identities, sampling/admission counters, outcome/mark allowlist, opaque correlation index, retrieval completeness, raw performance samples, payload/event totals, collector warnings, capability exclusions and teardown result. Preserve failure receipts. ## Disjoint module handoff API

- `view_telemetry_sink.py` keeps the agreed subprocess CLI `--output`/`--receipt`. An additional independently tested `telemetry_sink(output_dir, run_id)` context owns only its loopback receiver/thread and returns immutable `endpoint/service/output`, a fresh four-key synthetic `env`, and `assert_receipt(path_or_dict, timeout<=15)`. Existing harness may use the CLI and retain processgroup ownership; no requirement to switch lifecycles. Imports require explicit `uv --with opentelemetry-proto==1.39.0` in the harness environment; imported PEP723 metadata does not install dependencies.
- `ui/scripts/qualify-view-telemetry.mjs::runTelemetryChecks({page,context,baseURL,serviceName,runId,outputDir,fixtures})` is an initial-open/raw-overhead helper only. `fixtures` carries existing `aggregates`, authoritative `identity:{appSource,frontendSource,serverInstanceId}`, and optional private synthetic `forbidden` sentinels. It owns and closes at most64 fresh contexts; same-origin loopback destinations are checked after fixture URL resolution. Actual finite request IDs must belong to each report's `request` correlations (they are distinct from journey `open_id`); the unsampled arm must have zero POSTs. The helper writes `telemetry-browser-result.json` with exact expectation inventory and all raw trials, excludes warmup/reset observations from cohort counts, and never returns overhead clearance. CDP post-navigation counters are retained raw without subtracting an unrelated about:blank baseline. This helper has contract tests but has not run against a Phoenix candidate. Physical/background/resume/terminal capability coverage remains explicitly unexercised in this helper and must be added before full acceptance.
- `tests/e2e/assert_view_telemetry.py::assertPhoenixTelemetry(output,service_name,run_id,expected_cases,forbidden=(),*,drain_receipt)` reads final reconciled capture after the owner stops/drains the app and receiver. CLI accepts corresponding `--output --service-name --run-id --expected-cases --drain-receipt --receipt`. The mandatory owner-authored drain receipt is exactly `{run_id,service_name,app_stopped:true,receiver_stopped:true,errors:[]}` from observed lifecycle completion, not an invented readiness flag. Expected cases may be the browser result path. Missing/extra exported journeys, browser failure, unknown projections, wrong identity/timing/correlations or late export/retention failure reject. It validates semantic export of the stated cases; it does not upgrade an explicitly partial browser result to full acceptance.

Current independent controls: ten compiler-free sink/context/final-helper tests and five Node sampling/cohort/destination/request-identity tests. The existing history owner alone adds the opt-in post-scrub environment/server/workflow calls after frozen evidence is preserved; no shared harness file was edited here.
