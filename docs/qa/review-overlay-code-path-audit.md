# Review message: source-first delayed-motion audit

## Conclusion and evidence boundary

The earlier short static browser windows did **not** exhaust source investigation. This audit identifies concrete routes that those windows did not stimulate. The strongest new overlay-local candidate is **background projection churn → new annotation callback → replacement Markdown component types → Mermaid remount → loading-placeholder/SVG geometry change**. It needs no image and no new touch. With plain unchanged prose, the same replacement does not by itself prove unequal layout or motion.

Other concrete gaps are an uncancelled clipboard fallback selection after a deferred rejection, a missing touch-cancellation binding for an armed long press, and background focus effects without overlay ownership guards. These are reachable source mechanisms, **not proof of the reported iPhone displacement**. No generic focus suppression, product correction, production mutation, or repeated browser matrix was performed.

References below are exact source lines at `80c49753d0ec39fc9c52838aede6c6a2e1abcde7`; this document does not make them normative requirements. The original [browser report](review-overlay-idle-audit.md) remains evidence only for its static conditions.

## Ranked findings

### 1. Background data can invalidate Markdown component identity, with delayed non-image layout changes

**Class:** credible unintentional delayed layout trigger; native scroll/clamp/anchoring consequences unresolved. Strongest genuinely no-fresh-touch overlay-local path found.

**Complete chain:**

1. `conversation/atom.ts:866–878`: accepted `sse_conversation_update` or browser-session updates replace the conversation object. A selected old message need not change.
2. `pages/ConversationPage.tsx:1846–1890`: projection effect emits a new object literal; cleanup publishes null. Dependencies include conversation/authoritativeConversation, pendingMessages, archive/composer/callback state. There is no semantic equality or viewed-message-content guard. `useConversationAtom.ts:53–98,121–144` does preserve selected-view identity when selected fields are unchanged: this is **not every heartbeat/token**. Streaming request-ID changes are included in the selected view; ordinary deltas for the same request need not change it. An accepted conversation-object change is sufficient. Pending-message arrays are another source (`ConversationPage:771–781`, `useMessageQueue.ts:58–104`).
3. `pages/ProductConversationPage.tsx:932,956–960,1692–1707`: embedded live page publishes through setLatestProjection. Parent keeps the same projection object after live-authority/conversation-ID checks; no equality filter. Cleanup-null and next publication may batch: the mechanism does not require null to paint.
4. `ProductConversationPage:1020–1025`: appendAggregateReviewNotes depends on the **whole currentLatestProjection**, so its function identity changes. It is supplied as MessageViewer.onSendNotes at `1737–1753` when live controls and append capability exist.
5. `MessageViewer.tsx:204–207`: startAnnotate depends on onSendNotes. Its identity changes despite unchanged selected content. `145–150` passes it to MarkdownViewerBody.
6. `viewer/MarkdownViewerBody.tsx:89–145`: useMemo depends on onAnnotate and constructs **new function component types** for paragraphs/headings/list/table/blockquote/code. React replaces those subtrees when types change. No stable component boundary separates callback updates from renderer identity. MessageViewer and its sibling AnnotationDialog do not need to remount.
7. The code renderer (`130–143`) contains MermaidDiagram. A new instance initializes in rendering mode (`MermaidDiagram.tsx:80–92`), then its effect (`100–157`) imports/renders Mermaid and replaces `Rendering diagram…` with SVG (`198–216`). CSS (`index.css:1481–1494,1528–1535`) has no previous-height reservation. A rendered tall diagram can collapse to the placeholder then expand after async completion; diagram/source preference also resets. A diagram above the current reading point can affect layout without a nearby image.

**Prerequisites:** live writable product owner, append capability supplied, a listed projection dependency changes, viewed message remains present. Guards for capability: `ProductConversationPage:961–967,1409–1417,1500`; producer `ConversationPage:1831–1844,1859–1862`. If onSendNotes remains undefined, this particular callback path does not churn. An actual content or theme change can independently rebuild the map.

**Frequency/late work:** can repeat per qualifying background update, unlike a once-only mount effect. Mermaid suppresses obsolete completion with cancelled checks in its promise chain (`116,133,146`); cleanup marks cancelled, removes measuring node and revokes URL (`149–155`). Its rAF callback checks cancelled (`139–142`). These guards protect an obsolete instance, **not unnecessary fresh instances**. Existing pending render is not aborted; late old state is suppressed.

**What is proved / not proved:** replacement component identities and asynchronous distinct layout states are source-backed. Plain prose can be replaced at equal geometry in one commit; neither replacement nor loss of anchor-node identity proves scrolling. Viewer has no explicit correction for this remount path. Browser anchoring/clamping depends on height, anchor eligibility, position and engine. The static plain-prose fixture lacked both live projection updates and diagrams, so its zero-motion result cannot falsify this mechanism.

### 2. Copy can perform a late global selection mutation after its originating owner changes

**Class:** credible unintentional delayed selection/focus-affecting trigger, contingent on earlier Copy; native scroll consequences unresolved.

`MessageViewer.tsx:79–81` renders the actual CopyButton. `CopyButton.tsx:48–61` awaits copyToClipboard. `utils/clipboard.ts:9–17` awaits navigator.clipboard.writeText; rejection falls through to body append → temporary fixed opacity-zero textarea → **select()** → execCommand → remove (`19–31`). No lifetime/generation/active-owner guard, AbortSignal, or focus/selection preservation is present. There is no explicit focus call: native focus/scroll consequences of selection remain unmeasured. Fixed/transparent styling is not cancellation or a native selection safety guarantee. The destination is document.body, outside viewer ancestry.

`CopyButton:32–46` resets copied state/timers for text changes/unmount; it does not cancel the pending clipboard promise. A late success can also install an icon-reset timer after prior cleanup, but that timer changes icon state, not scrolling. An unavailable clipboard takes fallback immediately; a delayed rejection is the no-new-touch route. Repeated Copy requests can each continue.

**Targeted disposable discrimination:** Node v26.8.2 imported the **actual** clipboard.ts directly, with a stub navigator/document (no installed packages/build/browser). A deferred writeText rejection released after an owner-change marker produced exactly `writeText → owner changed → append → select → execCommand → remove`. Assertions passed. This establishes actual-source continuation ordering/lack of cancellation, **not actual DOM focus or pixels**. No copied text/private data was used.

### 3. An already-armed long press can survive touch cancellation and mount the autofocus editor

**Class:** credible delayed trigger with a concrete missing cancellation binding; requires an earlier gesture, never a timer from nothing.

`AnnotatableBlock.tsx:35–40,52–58` installs useLongPress at 500ms/10px. `useLongPress.ts:33–54` arms one timer and captures the then-current onLongPress; the timer calls it without a generation/visibility/gesture-active recheck. The long-press callback at `AnnotatableBlock:35–36` invokes annotation with that line/text (the separate explicit button does so at `66–69`) → `MessageViewer:204–207` sets annotating → `121–129` mounts AnnotationDialog → `AnnotationDialog.tsx:39–41` calls textarea.focus() without preventScroll.

Movement >10px cancels (`useLongPress:57–68`); touchend/mouseup/mouseleave cancel (`AnnotatableBlock:54–58`); disabled-effect and unmount cleanup cancel (`useLongPress:71–79`). **There is no onTouchCancel binding.** Cancellation that arrives without a handled movement/release can leave the earlier timer armed until it expires. Callback change is not a cancellation dependency: a still-mounted block keeps the previously captured callback; renderer replacement unmount does cancel. The start callback itself checks enabled when armed, not again when fired; a subsequent disabled effect cancels once committed.

After mounting, ordinary dialog rerenders do not refocus: its focus effect is `[]`. Changes in editor body/dirty callbacks update the separate dirty effect (`35–37`) and key listener (`43–57`), not autofocus. Dirty state does not open an editor. No runtime claim that the observed iPhone event included cancellation is made.

### 4. Background sibling focus effects are not excluded by the open overlay

**Class:** credible delayed/background focus triggers, coordinated with the transcript owner; physical ancestor/viewport motion unresolved.

- `QuestionPanel.tsx:343–352`: effect on `[currentStep,currentQuestion]` queues rAF → panelRef.current?.focus(), without cancelAnimationFrame, preventScroll, scope/overlay guard or captured generation. An accepted new-sequence state/reconnect event can replace the question object for the same request, according to the transcript-owner audit; duplicate/out-of-order events and ordinary tokens preserving phase do not. If still mounted beside the mobile viewer, the panel can take focus in the next frame. If unmounted, its null ref generally makes the old callback a no-op. Not periodic.
- `InputArea.tsx:236–239`: a nonzero focusToken causes textarea.focus() on mount or token change, without consumption/preventScroll/overlay ownership. Parent `ConversationPage:568–571` increments the token; notes (`1772–1791`) and other intentional composer actions request it. A later question→normal/recovery remount can replay an old nonzero token without a new action. Same mounted unchanged-token rerenders do not refocus. Route-autofocus guards elsewhere do not constrain this effect.
- `ViewerShell` has aria-modal for dialog modes but no inert sibling enforcement or actual focus trap. `useRegisterFocusScope` only pushes/pops shortcut scope (`useFocusScope.tsx:186–192`); it does not stop these focus effects. Overflow-hidden ancestors are programmatically scrollable, so hidden/covered does not establish safety. Whether focus produces Safari viewport/ancestor movement requires measurement; the focus calls themselves are source-proven.

The transcript owner confirmed these paths are unchanged at the RC6/baseline pins. Their separate Find finalization defect is **not** evidence about MessageViewer.

## Browser-induced layout/selection paths without explicit scroll APIs

- `.viewer-content` (`index.css:4920–4925`) is flex/min-height0/overflow-y:auto/overscroll-behavior:contain. Shell body modes use overflow:hidden (`11225–11239`). Containment governs chaining, not all programmatic/native reveals. Overlay is fixed 100dvh (`11034–11045`); keyboard/visualViewport changes can move/resize visible content independently of scrollTop.
- Mermaid initial async completion, callback-induced remount and note-highlight expiry can change heights as detailed above. Plain fenced-code highlighter in this viewer is synchronous (`utils/syntaxHighlighter.ts:70–84`); the separate transcript's deferred syntax-highlighting timer is not used by this renderer.
- Actual selected-message content updates rebuild Markdown (`MessageViewer:30–41,145–150`, MarkdownViewerBody `145`); live content is not frozen by opening review. That is a conditional data/layout update, not a self-triggering scroll loop. A settled historical message with unchanged content excludes this particular cause but not projection-callback churn.
- Theme context changes rebuild code renderers (`MarkdownViewerBody:82,145`), and a mounted Mermaid rerenders on `[diagramId,source,theme]` (`MermaidDiagram:157`; normalized source at `87`). `useTheme.ts:12–25` reads initial preference. `ThemeProvider.tsx:12–32` updates data-theme/meta/manifest/storage and registers an OS media-query change listener, not polling. That listener only updates state if the storage key is absent, while the initial theme effect writes the key; ongoing automatic system-following must not be assumed. A fresh explicit theme change is intentional; initial lazy module/font/diagram completion is not necessarily immediate.
- SauceCodePro NF Mono faces use font-display:swap (`index.css:3–34`); where those faces are used, a pending font can reflow text once loaded. This is a finite platform/resource layout source, not an app timer or a claim of font loading at the incident. No viewer-local image is needed. No broad font/platform theory substitutes for the concrete callback-remount path.
- CSS annotation-highlight repaint (`components/useAnnotationHighlights.ts:18–43` and reaction-range helpers) creates paint ranges rather than changing window Selection. Expanded document.body observation may be scheduled by overlay mutations but does not focus/scroll/open an editor. Native text selection loss on Markdown replacement remains browser-dependent; there is no app Range restore in MessageViewer.

## Coverage, prioritization and remaining uncertainty

Source investigation covers both event dispatchers, product/legacy slot owners, URL restore, provider/store and selected-message identities, every viewer-local focus/scroll/selection call, note jump/save/delete/clear/exit (no existing-note edit action is exposed), delayed gesture callbacks, portal relocation, renderer identity and async Mermaid layout, direct clipboard continuations, theme/fonts, and coordinated background focus/reader effects. Independent read-only reviews challenged mount/hydration, shell/exit, and projection→Mermaid paths. No new broad matrix, dependency install or native build was used.

**Prioritize the projection/callback/renderer identity boundary**, not blanket focus suppression: it supplies a repeatable no-touch cause of real DOM/layout replacement while reading an unchanged old message. The smallest discriminating regression would hold selected Markdown constant, publish a new eligible live projection, and assert the paragraph/code/Mermaid instance and its selected mode stay mounted. A targeted geometry check with an already-rendered diagram above the reading point can then establish whether that proven replacement moves text. A static prose idle wait cannot answer it.

Other bounded discrimination targets, not generic capture requests: arm a hold then dispatch touchcancel and assert no editor at500ms; resolve/reject a pending Copy after owner change and verify no unauthorized selection; replace a still-mounted question object with review open and observe focus ownership. The clipboard leaf ordering test already establishes its unguarded continuation, but no native scroll assertion.

No source finding yet uniquely identifies the tentative physical iPhone symptom. What remains specifically uncertain is native anchoring/clamping after the proven asynchronous layout boundary, native selection/focus viewport response in the concrete delayed paths, and which prerequisites existed at the incident. These uncertainties are narrower than “Safari might scroll.” They do not justify suppressing all focus or declaring the investigation exhausted on a negative short-window result.
