## Candidate A: compact the cleared-result marker

The current marker (`runtime/executor.rs`, `cleared_tool_result_marker`) is
`[tool result cleared to save context] [persisted source: conversation=<uuid>, message=<uuid>, sequence=<n>]`.
That is about 150 bytes, with two UUIDs that tokenize badly. The conversation ID is the same for every marker in a
transcript, and clearing only applies to the current transcript's own messages. Round 1
priced markers at **2.127B token-turns, about 3.5% of input**.

The proposed marker is `[tool result cleared; seq=<n>]`. That keeps REQ-STR-004 (a marker, not a gap) and
REQ-STR-012 (a source locator), with the transcript implicit and the sequence as the locator.

Replay:
1. The current marker's token count from your calibration, and directly from its bytes.
2. Token-turns for the current versus the proposed marker under the reconstructed sweep schedule.
   Give the saving as a share of recorded input.
3. Whether any transcript ever had a cleared result from a different transcript in its
   rendered history (should be 0). Count only, no IDs.
4. How often, after a marker appears, the agent later calls `read_conversation` or another tool
   that dereferences it. This tells us whether the locator is used at all.

## Candidate B: patch diff as a clearable preview with a durable record

Patch results are nonclearable (REQ-STR-002 treats them as "the record that a change was
applied"). They carry **4.734B, about 7.8% of input**. The tool-call input that stays
in the assistant message already records what was requested. The proposal splits the result in two:
- a **durable record**, never cleared:
  `<patches_applied>all</patches_applied>`, the path, one `@@ -a,b +c,d @@` header per
  hunk, and the autogenerated warning if there was one;
- a **clearable preview**: the `<diff>` body, cleared on the normal sweep schedule.

Replay:
1. The record size distribution (tokens p50/p90/p99), computed from the stored diff.
2. Token-turns when each patch diff is cleared at the first reconstructed sweep whose
   watermark passes it, against the current figure. Give the saving as a share of recorded input. Separately, the change in
   overall sweep gain (patch diffs make each sweep larger), which can delay the next sweep.
3. Information-risk proxies: how often, after a patch diff would have been cleared, the agent
   later (a) reads the same path (hashed), (b) runs `git diff` or `git show`, or (c)
   re-patches the same path with an input that fails. Compare these rates with patches whose diff is still
   retained at the same distance, to see whether clearing would plausibly force extra reads.
4. The share of patch results that are errors (10.9% in round 1). Error results keep
   their full text under this proposal; confirm their carry.

### B · Durable patch receipts and clearable diff previews

- **3,388.5M token-turns saved (5.57%)** using the path already recorded in the tool call. Including a new explicit path field in the receipt gives **3,242.5M (5.33%)** after accounting for its carry on every recognized success.
- 62,047 successful patch results had recognized previews and 38,118 previews cross a reconstructed sweep. Current patch output carry is 4,733.7M, moving to 1,345.2M before any explicit path duplication.
- Receipt sizes at p50/p90/p99 are 24.0/49.0/79.4 estimated tokens with the path in the producing call and 41.9/71.9/103.5 with an explicit path field. The replay preserves warnings, post-diff metadata, hunk coordinates, and truncation notes. 0 of 118,623 hunks have additional context on the header line beyond its coordinates.
- Patch errors stay intact. 7,807 of 71,597 results (10.90%) carried 131.1M token-turns.
- Adding previews increases aggregate gain on the fixed schedule by 18.6M local-estimator tokens (4.13%). 5,946 of 14,006 sweeps gain additional tokens, with p50/p90/p99 2,034/7,430/15,279. A changed schedule would need a separate replay with request pressure and eligibility recalculated at each request.

### Worker votes

- **A · Disagree with the sequence-only marker as written.** The current exact-message reader resolves message IDs. The replay found three calls to that reader explicitly targeting cleared results. Preserve a resolvable message ID in the shorter marker, or add and test an exact same-transcript sequence lookup where the marker is emitted. Then replay the exact revised format.
- **B · Agree to a typed prototype PR.** The modeled gain is 5.33% with an explicit path. Keep the applied-effect receipt, all error text, and the stored diff preview retrievable. Git evidence lookups are more frequent in the cleared cohort at the oldest ages. The merge vote requires the exact implementation replay and a verified retrieval path.

The replay uses a fixed schedule and estimates input tokens from UTF-8 sizes. A revised cache prefix, retrieval, or changed sweep timing can affect net savings. Candidate percentages are separate scenarios.
