MCP servers can send server-initiated JSON-RPC requests -- notably ping, which the MCP spec says receivers MUST answer promptly. Phoenix currently forwards server-initiated messages (requests and notifications) to the protocol-layer ServerMessageSink, which handles notifications/tools/list_changed and logs-and-drops everything else, so a server ping goes unanswered and a liveness-checking server may consider the client unresponsive. Answering requires a reply path from the sink back through the transport: trivial for HTTP (POST the response message), but for stdio the round-trip stdin+stdout lock is held while the sink runs, so a synchronous reply would deadlock -- the response must be queued and written after the in-flight exchange completes (or the stdio write path restructured). Scope deliberately excluded from the M2 transport substrate (tools-only surface, and the gap predates it: the pre-trait code dropped id-bearing server requests as mismatched responses). Implement ping replies across both transports; other server-initiated requests (sampling/elicitation/roots) stay out of scope per specs/mcp/ non-goals.
