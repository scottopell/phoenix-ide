# Support opt-in 872K context on the Codex bridge

Phoenix currently caps every Codex-bridge model at 272,000 tokens in `ModelSpec::context_window_for` (`crates/phoenix-llm/src/models.rs`), with `CODEX_BRIDGE_CONTEXT_WINDOW` as the shared authority. This affects registry metadata (`/api/models`), input/output headroom, context indicators and continuation/compaction decisions. Direct OpenAI API model context remains independent. Add a deliberate opt-in way to use the larger Codex context where the account/model backend supports it, without raising the default or falsely expanding older/other models. Implement this task in its **own PR**, separate from model registration PR #801.

## Upstream evidence and terminology

- The official Codex catalog for `gpt-6-sol` and `gpt-6-luna` reports `context_window: 272000`, `max_context_window: 872000`, and `supports_experimental_context: false`. Model entries arrived on 2026-09-22 in `openai/codex` commit [`49e95cc73f4`](https://github.com/openai/codex/commit/49e95cc73f4). See [`codex-rs/models-manager/models.json`](https://github.com/openai/codex/blob/25270df2615eb4da5b9d4a9a392226933fb096c5/codex-rs/models-manager/models.json).
- The upstream opt-in is `model_context_window = 872000` in Codex config. [`with_config_overrides`](https://github.com/openai/codex/blob/25270df2615eb4da5b9d4a9a392226933fb096c5/codex-rs/models-manager/src/model_info.rs#L19) clamps that override to `max_context_window`. This appears to change client budgeting/compaction; no dedicated context-size request header/body field was found. Verify against the current backend contract before changing Phoenix limits.
- This is **not** Codex's separate experimental context-management/history-notes feature. Sol/Luna set `supports_experimental_context: false` in the catalog. Do not gate this task on that unrelated feature flag.
- Codex defaults to 272K; 872K is a maximum opt-in budget, not a new default or the 1.05M direct OpenAI API window. Upstream uses 90% of configured context as the default auto-compaction threshold. Phoenix has its own headroom and compaction policy: adapt it intentionally, not by copying that threshold blindly.
- OpenAI API billing explicitly reprices requests above 272K input (2× input/cache and 1.5× output for the *entire request*). **No published evidence establishes the same 272K discontinuity for ChatGPT-sign-in Codex credits or included subscription allowance.** Codex credit rates are published per model/token category without long-context bands. Keep cost/allowance claims separated by route and avoid fabricating a Codex multiplier.

## Implementation investigation

1. Trace the selected model's real Codex route and account-catalog metadata through `ModelRegistry`, `ModelSpec::context_window_for`, request output reservation, token accounting, context indicators, stale-tool-result clearing, Phoenix Continuation and recovery. Find one authority for the configured effective window; avoid a separate UI-only override or guessed global constant.
2. Choose and specify the opt-in surface (server configuration, conversation setting, or model-route choice) with a clear default of 272K. Confirm whether `gpt-6-astra` or other Codex models should share 872K only from their catalog evidence; do not infer from `gpt-6-*` naming. A model switch, account change, unavailable catalog entry, or route switch must not silently retain an unsupported large window.
3. Check whether the ChatGPT/Codex backend actually accepts a >272K request for the authenticated account. Use a bounded synthetic test where authorized; no private prompt content or credentials in logs. Distinguish client context budgeting from a server-enforced maximum and classify a backend rejection clearly.
4. Preserve current default behavior and per-request headroom. Keep direct API's 1,050,000 window unchanged. Do not add an undocumented request header or change Codex's `supports_experimental_context` flag.
5. Add focused tests for default 272K, opt-in 872K, model/route/account gating, switch/restart persistence as applicable, output headroom and compaction near limits, and clear user-visible metadata. Run `./dev.py check` and update the normative LLM/context requirements and executive status; add an ADR only if the opt-in policy changes architecture or compatibility guarantees.

## Acceptance

An eligible Codex-authenticated Sol/Luna conversation can explicitly opt into an effective 872K window, and Phoenix's registry, runtime decisions, and UI agree on that effective value. An ordinary Sol/Luna Codex conversation stays at 272K. Unsupported models/routes never advertise the larger value. Backend rejection, context exhaustion, and recovery are explicit and do not mutate or silently truncate the user's transcript. Usage/cost surfaces do not assert an unverified Codex quota pricing step.
