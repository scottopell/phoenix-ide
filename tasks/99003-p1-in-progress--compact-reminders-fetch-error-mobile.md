# Keep reminder fetch failures compact without hiding reminder truth

## User-visible problem and evidence

A user screenshot of mobile web Phoenix shows a conversation transcript followed by a large bordered Reminders panel containing “Load failed” and “Retry” above the composer, while the bottom status says connecting. A background GET failure should not reserve reminder-card space or needlessly move transcript/composer on an iPhone. The exact screenshot route/viewport is not known; reproduce on canonical ProductConversation and standalone conversation layouts.

On this checkout (`5f72f6178`), `ui/src/reminders/RemindersPanel.tsx` renders the full `<section class="reminders-panel">` when `loadError` is set and no cards exist; `RemindersPanel.css` gives that section border/padding/margins and `flex-shrink: 0`. `ConversationPage.tsx` mounts it before the transcript, including in `ProductConversationPage.tsx`'s embedded composer region. `StateBar.tsx` already presents connecting/reconnecting/offline state. `useReminderRefresh.ts` provides abort, five-second/focus/online polling and request coalescing. Prior successful rows survive a fetch failure but are not explicitly identified as stale. `RemindersPanel.test.tsx` covers due cards, revision conflict, owner isolation, and coalescing; it does not cover fetch-failure UI or recovery. `specs/reminders/requirements.md` REQ-REM-006/008 require revision-checked management and visible due truth. Existing task 44021 concerns the original feature, not an established current source owner of this correction.

Make the initial/unloaded GET failure a small, unobtrusive, accessible inline reminder status with manual Retry and useful failure details on demand, not the full bordered/scrollable card; do not conflate unloaded/unknown with a successfully loaded empty list. Avoid a second alarming network banner when the existing connection status already reports disruption. 3. On refresh failure after a successful list, retain cards and visibly but compactly label them as last-known/stale until a successful fetch. Do not imply create/cancel/reschedule succeeded after a failed/uncertain mutation; do not automatically replay mutations. A confirmed POST followed by a failing GET must not be represented as a refreshed list. Preserve current revision-conflict safety and owner/abort isolation.
4. Preserve bounded, coalesced reads; repeated poll failures must not add layout height or trigger request spam. Prefer existing component/test/CSS mechanisms over a new offline subsystem or global error architecture.
