# Unified request capacity and context preservation implementation plan

Scope: implement the context policy specified by specs/llm/requirements.md REQ-LLM-004j through 004m, bedrock REQ-BED-020a, stale-tool-results REQ-STR-012 and analytics REQ-AN-011. Planning/specification only in this change; runtime delivery remains pending. Production incident evidence: task 45021 in primary checkout; deployed 9ebd9d8, two local preflight failures persisted generic notices as handoffs.

## Delivery order

1. Capacity boundary and incident recovery. Introduce a common immutable prepared-request plan with exhaustive ready, needs-compaction, and cannot-fit outcomes, keeping local pressure distinct from provider rejection. Reserve declared model maximum; do not shrink it based on effort. Route parent pressure after permitted clearing into existing durable compaction. Preserve subagent terminal semantics. Stop generic notices becoming handoffs. Reuse current continuation identities/recovery; do not add a scheduler. Validate below-90% pressure, tool-result growth, protected-input failure and one-successor restart/idempotence before supported recovery of the two production transcripts. Recovery/deployment are separate operational steps.
2. Shared accounting and model switches. Ordinary and tool-free handoff requests share route limits and accounting; they retain distinct assembly/retention rules. Freeze provider-final input, settings, route and guidance version; invalidate plans on mutation. At the next request boundary, a model/route switch rerenders portable history and drops incompatible transport/private state under existing provider contracts. Validate large-to-small windows, round trips, historical tool pairs, images, and safety revocation.
3. Counting improvement. Add optional route-declared provider counting and verified local tokenizer/template implementations behind one counting result. Unknown capability uses conservative local estimation. Only query remote counting when local planning would otherwise reduce context or reject; one attempt with 2-second deadline per frozen candidate, no retry. Counting failure falls back visibly. Do not add model downloads, capability probes, or durable counting jobs. Compare complete-request predictions with actual matching provider usage; never infer token-count identity from a model alias alone.
4. Retention and cache stability. Keep persisted transcript authoritative. Keep recent paired tool results, accepted handoff and interpretation/decision rows; retain source locators on cleared results. Batch monotonic clearing under existing worthwhile-sweep policy. Keep user-turn guidance stable through tool loops, refresh at next turn; retain live authority. Validate no accidental historical restoration, reordered declarations, or prefix changes on unchanged input. Use one handoff pipeline with existing Coordinator prompt; no extracted memory database or separate strategy engine.
5. Explainability. Extend existing request metrics and /usage with capacity source/uncertainty, input/output allocation, reduction counts, classified prefix-change cause and observed cache reuse. Link reductions to original request identity, including local rejections without provider attempts. Store scalar facts relationally; derive aggregates; do not duplicate transcripts or store content hashes as durable memory. Show unknown attribution honestly. Validate privacy and missing-usage behavior.
6. Qualification. Deterministic fixtures cover cold/warm requests, worthwhile clearing, compaction/rewarm and model switches. Measure input/cache/output, planner error, TTFT, attempts and semantic continuity separately. Coding and Coordinator fixtures test corrections, provenance, unresolved commitments and completed work. Run focused tests, Allium checks, spec-shape, codegen if needed and ./dev.py check on each implementation slice. No live near-window stress or unbounded quota use.

## Scope limits and acceptance
No new memory authority, provider framework, automatic model fallback, budget setting, persistent refresh bundle, token-count service, cache-hit promise or new recovery workflow. Common accounting is not identical provider serialization. Cached tokens still consume context. Correctness and explicit user model choice outrank cache preservation. Existing tool authority/revocation and close/admission fences remain authoritative. Partial implementation must report which numbered slices and requirements remain undelivered; source-ready is not production acceptance.
