The stale-tool-result clearing pressure signal (get_last_turn_prompt_tokens) orders turn_usage by created_at, but insert_turn_usage is written from a detached task in the executor, so created_at/rowid reflect insert time, not conversation turn order. If two turns inserts race, the query can return a stale prompt size and the clearing planner holds or sweeps on wrong pressure. Low risk in a serialized conversation (insert is fast, the LLM turn between is slow), so deferred from PR #330. Fix by tying usage to the assistant message sequence_id (and ordering by it), or by caching the last reported prompt size in memory on the runtime (like the clear-watermark cache), lazy-initialized from the DB on restart. specs/stale-tool-results, REQ-STR-001.
