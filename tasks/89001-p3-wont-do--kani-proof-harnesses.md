Add Kani model-checking proof harnesses for two bounded, panic-prone cores,
behind an opt-in `./dev.py check` lane. Attempted, verified-once, then shelved
(`wont-do`) for two blockers below. The full implementation is inlined as a
git patch at the bottom — `git apply` it to resurrect.

## What we built

1. **terminal ring buffer** — extracted the `RING_CAPACITY` evict-then-push in
   `CommandTracker::handle_osc133_d` into a generic `ring_push<T>` helper and
   proved `len <= RING_CAPACITY` and newest-at-back over a bounded
   nondeterministic push sequence.
2. **patch char-boundary truncation** — extracted the walk-back-to-char-boundary
   in `is_autogenerated` into `safe_truncate_end(content, max_len)` and proved
   the returned offset is always a valid char boundary `<= len`, so the slice
   `&content[..end]` cannot panic on a multi-byte char straddling the cut.
3. **dev.py `kani` lane** — opt-in, skip-if-absent, path-gated on the harness
   files, scoped with `-p` to harness crates, parallel (own goto-c target dir,
   no workspace target-lock contention), per-step timeout-guarded.

Both refactors are correct-by-construction and behavior-preserving (existing
terminal + is_autogenerated tests pass unchanged). Harnesses are `#[cfg(kani)]`
so they compile out of normal builds; `cfg(kani)` is registered via workspace
`check-cfg` so `-D warnings` stays clean.

## Inaugural run: both proofs PASSED

- terminal `ring_push_maintains_bound_and_keeps_newest`: 0 of 526 checks failed,
  1.8s. Unwind assertion succeeded (bound fully explored).
- patch `safe_truncate_end_lands_on_char_boundary`: 0 of 279 checks failed,
  119s. Confirmed the std `slice_error_fail` panic path is unreachable.

## Why shelved (wont-do, for now)

1. **MSRV mismatch (hard blocker).** Kani 0.67 pins its own nightly
   (nightly-2025-11-21 / rustc 1.93), older than the workspace
   `rust-version = "1.94"`. `cargo kani` errors in cargo's MSRV resolution
   *before verifying*. The proofs only ran after temporarily stripping the
   `rust-version` lines from every crate. So on a normal dev/CI machine the lane
   can only **skip**, never verify, until Kani ships a >=1.94 toolchain (or the
   project lowers MSRV). The lane was written to classify this as a graceful
   skip, but that means the harnesses give *verified-once*, not *continuous*,
   protection — not worth carrying the lane + cfg machinery for that.
2. **Slow solve.** The patch harness takes ~2 min (CBMC over `from_utf8` of
   arbitrary bytes is solver-heavy). Within the lane timeout, but it dominates
   `lane_rust`'s wall-clock on a warm incremental build, eroding the
   "stays in lane_rust's shadow" property the lane depends on. Tunable by
   shrinking the byte bound 4 -> 3, at some coverage cost.

## How to resurrect

1. `git apply` the patch below (onto a tree at or after the bash_check proptest
   commit).
2. Install Kani: `cargo install --locked kani-verifier && cargo kani setup`.
3. Resolve the MSRV mismatch — either Kani has caught up to the workspace
   `rust-version`, or temporarily strip the `rust-version = "1.94"` lines for
   the run (`perl -ni -e 'print unless /^rust-version/' crates/*/Cargo.toml`,
   restore with `git checkout`).
4. `cargo kani -p phoenix-terminal -p phoenix-tools`.
5. Consider tightening the patch harness byte bound if solve time matters.
