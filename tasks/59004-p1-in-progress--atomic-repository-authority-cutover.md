# R2 — Atomic repository authority cutover

## Problem and single goal

Phoenix's live repository authority is still the legacy `Project` representation: canonical path is treated as identity, `projects.main_ref` supplies canonical-default/fork behavior, `conversations.project_id` drives creation and cleanup, and Project rows feed API, startup, task, fork, and lifecycle paths. Merged Repository Foundation adds the hidden `GitRepository` substrate, deterministic legacy backfill, dormant `WorkScope.repository`, and read-only shadow validation, but Foundation data is not live authority.

R2 has one goal: perform one atomic reader/writer cutover so every correctness-sensitive repository decision flows through `ProductConversation → WorkScope.repository → hidden GitRepository`, while any temporarily surviving Project-shaped output is a typed read-only projection from that authority. This is an authority transition, not a rename and not a product-surface redesign.

## Authority transition

### Before R2

`Project` is the sole live repository authority. Foundation hidden repository rows and `WorkScope.repository` attachments are migration-seeded strictly by Project ID and remain dormant read-only shadow data. Distinct Project IDs therefore remain distinct even when later R2 observation may prove linked worktrees share one Git common directory. Locator/default observation tables are validly empty after Foundation catch-up and validation because Foundation performs no live probes. Production behavior continues to consult/write Project; no shadow mismatch or absence may be repaired by writing both models.

### After R2

`WorkScope.repository → hidden GitRepository` is the sole live repository authority. A ProductConversation obtains repository context only through its attached WorkScope. Typed pre-scope provisioning evidence may name a hidden repository before a WorkScope exists as allowed by the normative specs. During the fenced transition, R2 resolves Foundation's Project-ID partition into steady-state identity from fresh typed observations captured under the same exclusion and authority generation: linked partitions converge only when each partition has a `present` Git common-directory observation identifying the same exact locator in the persisted observation set consumed by the G3 authority transaction. Separate clones remain distinct. Partial, missing, inaccessible, stale, or conflicting evidence remains typed/fail-closed and does not collapse identities; management-root paths, remotes, slugs, commit graphs, titles, and default-branch observations never prove sameness. Any retained `project`-named DTO, field, route, or report is a typed read-only compatibility projection/sink from hidden authority and cannot be written or consulted for correctness.

### Merged-main invariant

No running binary, worker, route, startup path, repair path, compatibility path, one-shot driver, background poller, or fallback can make a correctness-sensitive repository decision from Project, canonical path identity, current checkout as canonical proof, or a fabricated/default `main`. No semantic fact is written to both Project and GitRepository representations. Rollback cannot reactivate a binary or stale Project writer against state written after cutover.

## Frozen implementation PR brief

One PR owns the complete authority cutover. Separate commits are encouraged for reviewability—tests/gates, adapters, caller migration, compatibility reversal—but no intermediate commit may be deployed as a mixed-authority production state. Foundation is already merged; if R2 cannot move every remaining reader and writer together within one fenced deploy window, stop and replace this implementation authority rather than weakening the single-authority rule.

The implementation PR must keep the census below current. Every newly found repository-sensitive production caller must be added and classified before code changes are accepted. A caller may be deferred only when its current behavior is observational/presentational and the R2 implementation makes it structurally unable to write or flow back into correctness.

## Foundation readiness handoff and R2 final validation

Merged task 55006 defines two eligibility inputs with non-overlapping contracts. The typed database-readiness value binds the exact clean candidate implementation/schema, process-local database lifecycle, validator transaction/run, result categories, and bounded counts. The static source census binds its candidate SHA, census revision, content digest, and authority-leak conclusion. R2 consumes both values only when their candidate SHAs match. It never attaches the static census to the database run root, decomposes either value into mixable claims, or treats either as a lease on a database that Project writers can still change. Old-binary-on-new-database compatibility is unsupported and is not activation evidence; ADR-033/034's stopped-runtime paired restore is the only Foundation rollback acceptance.

After G1 proves continuous exclusion, its durable backend claim remains held while G2 launches the exact R2 binary in cutover-only mode. That process re-proves the claim and target, acquires the authority generation, and mints the process-local one-shot database/operation-bound Foundation capability. R2 consumes that capability in the same database lifecycle to invoke Foundation catch-up unconditionally and then runs Foundation query-only validation. This checkpoint must prove the deterministic Project-seeded repository set, exact WorkScope attachments, migration/schema/FK integrity, and Foundation's intentional valid-empty locator/default observation state. Catch-up and validation perform no live Git/filesystem/network observation and do not promote hidden data to authority.

Only after that valid-empty checkpoint does R2 collect fresh typed common-directory, management-root, and default-branch observations under the same exclusion and target authority generation. Observation capture may inspect the local Git/filesystem state, but raw paths, remotes, slugs, commits, titles, and branch names remain evidence rather than authority. R2 does not claim an atomic filesystem or Git snapshot across repositories: freshness is the per-observation status, provenance, generation, and observation time persisted as one complete set, and G3 consumes exactly that set. Every locator records exact `present`, `missing`, or `inaccessible` status, path, generation, and time; every default observation records resolved/unresolved status, branch when resolved, allowed provenance, generation, and time. Missing, inaccessible, unresolved, partial, stale, or conflicting evidence remains typed and fail-closed.

The fresh candidates enter one SQLite authority transaction. That transaction persists the complete observation set, runs the R2 final validator over repository/attachment equality plus observation completeness/value/generation/provenance, derives one complete convergence plan, applies it, makes superseded identities structurally unselectable, disables legacy Project mutations, records the irreversible authority generation, and activates hidden authority. There is no database mutation between final validation, plan derivation, plan application, and activation. For every group proven to share one Git common directory, all affected WorkScopes reattach to one surviving hidden identity and each non-conflicting semantic fact remains represented once. Separate clones and partitions lacking complete `present` common-directory evidence remain distinct. Any stale, partial, or conflicting claimed merge rolls back the transaction wholly.

The G3 authority transaction persists the minimal recovery receipt that distinguishes `pre-G3 abort-safe` from `G3 committed, roll-forward only` and binds the consumed cutover operation, matched G0 readiness+census pair, catch-up receipt/result, Foundation valid-empty validation, fresh observation set, R2 final validation, applied convergence plan, exact binary/schema identity, and committed target authority generation. Larger external artifacts may be written later, but crash recovery never depends on them. These are semantic bindings; this task does not prescribe a dump/copy/WAL command, artifact path, CI vendor, or serialization product.

## Old-binary and stale-worker exclusion

- Persist an authority/schema generation that every repository-sensitive writer checks structurally at DB open and before commit; pre-R2 binaries must be unable to satisfy it.
- Deployment must quiesce request admission, background creation/fork/PR/reconciliation workers, managed-worktree cleanup, standalone `drive-turn` processes, and every `./dev.py prod deploy`/`prod restart` backend before G3. PID absence alone is insufficient when durable claims, service-manager activation helpers, or queued jobs can outlive a process.
- In-flight creation claims, fork proposals, cleanup work, and background observation writes must either drain under old authority before G3 or be resumed only by the R2 binary from durable state under hidden authority. They must not straddle the authority transaction.
- Compatibility routes and old clients may read projections after cutover, but no old client request may invoke a legacy Project writer. Route-level “read only by convention” is insufficient; the adapter type/API must have no write capability.
- DB schema/trigger constraints must reject legacy Project authority mutations after G3 even if an old process reaches the database.
- Every server startup path, file DB opener, one-shot runtime, and repair utility must enforce the same minimum authority generation. No alternate opener may bypass the fence.

## Rollback and forward-fix posture

Before G3 commits, R2 may abort, roll back its uncommitted database transaction, and keep or restore the pre-cutover runtime only while Project remains sole authority. A binary-version downgrade follows ADR-033/034: stop Phoenix, restore the database backup paired with that binary, then start it. An older binary opening the migrated live database is unsupported. Task 44016 owns project-wide enforcement and product/deployment messaging for this offline downgrade boundary; R2 does not absorb a general backup, rollback, or matching-version subsystem.

After G3, rollback or bare-supervisor `prod restart` to a pre-R2 binary is prohibited: either could recreate stale Project authority or ignore post-cutover hidden writes. Because filesystem/service activation and the SQLite authority transaction cannot be one transaction, durable authority-specific backend claims must distinguish pre-G3 abort-safe state from post-G3 roll-forward-only state. Once G3 commits, recovery is roll-forward with the same hidden authority.

A post-G3 application failure may stop admission and deploy a fixed R2-compatible binary. It must not reverse the authority generation, copy hidden facts back into Project, re-enable Project triggers/writers, or consult retained Project data as fallback. An operator may perform the explicitly supported offline paired restore only with Phoenix stopped and the database backup paired to the target binary; that replaces the whole runtime/database state and is not ordinary cutover rollback or activation evidence.

## Compatibility projection contract

- Compatibility direction is hidden authority → typed projection/sink only.
- A compatibility projection may expose only existing client-needed presentation values, never hidden `GitRepository` identity.
- Existing branch-observation `repository_identity` strings are path/remote observations, not hidden identity. They may remain display-only only if structurally separated and renamed/typed so the backend can never populate them with, or accept them as, the hidden GitRepository ID.
- It may not accept writes, select a repository, resolve a canonical default, authorize cleanup, key a mutation lock, infer sameness, seed reconciliation, or feed its output back into hidden persistence.
- `project_id`-shaped filtering keys cannot be aliases of hidden IDs. If P1 still needs an old response shape, use an explicit compatibility-only token/value whose type cannot enter repository-domain APIs.
- `/api/projects`, `Project` DTOs, nested SSE-init `conversation.project_id`, top-level SSE-init `project_name`, sidebar filters, usage grouping, task listings, and global-read reports are allowed to survive R2 only where P1/C1 owns removal and only after they are proven read-only projections. R2 must remove any use of those surfaces as creation, cleanup, lock, fork, or lookup inputs. Compatibility values must be structurally distinct from hidden repository identity and from authority-bearing domain inputs; raw-string convention is insufficient.
- Recent location suggestions must follow REQ-API-001A: at most one present management-root locator per hidden repository, linked worktrees collapsed, separate clones distinct, ordered by surviving conversation/scope evidence, with no Repository collection or hidden ID.
