Pinned-threshold mismatch: the policy's `PIN_TO_BOTTOM_THRESHOLD = 100` px is nearly dead code because the only `viewportPinnedChanged` source is VirtualTranscript's 1 px `PINNED_EPSILON` edge — producing two opposite least-surprise violations.

(a) Scrolling down never clears unread unless the user lands within 1 px of the absolute bottom. `downwardMovement` never confirms tail return, and `handlePinnedStateChange`'s 100 px `domAtBottom` fallback only runs when the 1 px edge fires. Stop 2–99 px above the bottom — visually "at the bottom" per the policy's own threshold — and the chip stays, follow mode stays `reading`.

(b) Starting an upward scroll gets yanked back during streaming. When the user leaves the bottom, the 1 px false-edge fires while they are still within 100 px, and `handlePinnedStateChange` reports `atBottom: pinned || domAtBottom` = **true**. With an idle gesture (wheel; or on touch, when the scroll event beats the first `touchmove` delivery — likely with passive listeners and compositor scrolling) this runs `confirmTailReturn` → `following`, and the next streaming `heightChanged` issues an immediate `snapToLastIndex`, dragging the user back to the bottom mid-scroll. During active streaming height changes are constant, so this race is hit often — it reads as "scrolling up is janky / fights me for the first ~100px". It also leaves `geometry.atBottom` spuriously true after the user passes 100 px, since no further edge fires.

Fix direction: make the adapter dispatch policy-threshold crossings, not the physical 1 px epsilon — e.g. compute `atBottom` from each scroll snapshot against `PIN_TO_BOTTOM_THRESHOLD` in MessageList and dispatch `viewportPinnedChanged` on *policy-threshold* transitions (in both directions), instead of piggybacking on VirtualTranscript's `onPinnedChange`. Then delete the `domAtBottom` fallback, whose misreporting causes (b).
