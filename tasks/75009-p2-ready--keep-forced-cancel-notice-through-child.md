# Preserve the forced-cancellation notice through cooperative child drain

REQ-BED-005a requires one user-visible notice after forced cancellation completes. In `ConversationRuntime::handle_cancelling_tool_timeout`, the retained task is aborted and ToolAborted is applied, but the notice is emitted only if that immediately reaches Idle. If children remain, the parent enters CancellingSubAgents. A later cooperative final-child result reaches Idle without remembering or publishing the owed forced-tool notice. The separate child deadline emits a notice only when it fires.

Source proof: base `9441cd2824324e53697df88f4e9db07f6de3980e` and the spec-only branch have identical executor.rs blob `859dbd8dd4e690621c9a79decfd976404acdca7b`. Trace `handle_cancelling_tool_timeout` -> `process_event(ToolAborted)` -> CancellingSubAgents -> cooperative final `SubAgentResult`; `broadcast_cancellation_backstop_message` has no owed-notice path there. This is a source-confirmed pre-existing implementation gap, not a new runtime regression or an executed failure test.

Acceptance: force a tool cancellation while admitted children remain, let those children drain cooperatively before their own deadline, and persist/publish exactly one ordered completion notice after settlement. Preserve the immediate-Idle and child-deadline paths without duplicates. Add meaningful deterministic regression coverage; do not weaken cancellation requirements or replay tools. Runtime implementation is a separate, uncommissioned follow-up to spec work.

Scope qualification: the normative forced-retirement fact describes the current live cancellation chain. Existing generic restart/error paths may interrupt or replace that chain; they do not prove cancellation completed. Interrupted/restart notice handling is unqualified and not implemented. This task does not authorize a conversation-wide notice store or new automatic recovery guarantee; classify any proposed recovery behavior under the compatibility requirements before implementing it.

Related source-confirmed notice/error seam: `handle_cancelling_sub_agents_timeout` correctly terminalizes each pending child and calls `process_event(SubAgentResult)` on success, so there is no healthy direct-Idle bypass. On a terminalization error it logs and continues; the deadline has already been cleared, it is not rearmed merely by remaining in the same variant, and the user-cancel completion notice is emitted after the loop even if a target was skipped. Unknown cleanup-write authority is also reduced to the logged error rather than forwarded to the fatal fence. Qualify definite failure versus unknown local authority before reporting completion: a definite failure is an error without a completed notice, while unknown write authority closes the process fence under REQ-BED-033. Test partial drain, definite write failure and unclassified commit at deterministic barriers; preserve every admitted child's owed outcome and exact atomic parent acceptance. This is not a new retry/recovery guarantee or an authorization to repair runtime code in the spec-only task.

Preserve authentic terminal evidence racing a delayed delivery: atomically select the already-established child's exact raw payload/cause, or establish cancellation only if it is still nonterminal. Do not fabricate cancellation over a committed success/error. The DB helper currently locks and rejects a conflicting terminal record instead of overwriting it, but does not return that original payload; the executor logs the conflict and skips the child. Treat that as an existing conflict/delivery/liveness gap, not a source overwrite. Preserve the parent's separate intentional Timeout-to-TimedOut presentation policy when consuming selected raw evidence; this task does not authorize changing that policy or adding replay/recovery guarantees.
